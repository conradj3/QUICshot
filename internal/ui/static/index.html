Help

What this is

A local model of a Cloudflare-tunnel path, built on the same QUIC stack that cloudflared uses. Traffic flows:

blast → edge (HTTP/3, owns the 524) = QUIC tunnel = connector → origin

Reading the log

componentmeaning
edgeThe Cloudflare stand-in. Decides 524 / 1033 and logs every proxied request.
connectorThe cloudflared stand-in. Dials outbound to the edge.
originYour app. Its latency is driven entirely by the URL path.
runOutput of the current blast or probe, including the final summary.
uiThe commands this panel executed on your behalf.

What to look for

signalinterpretation
524The edge reached the origin but got no response in time. elapsed_ms matches the edge timeout, not the origin's delay.
1033No connector registered. The tunnel is down, not the origin.
client_deadlineThe client gave up first. The edge logs nothing at all, so this failure is invisible to Cloudflare-side dashboards.
quic_idle_timeoutThe connection died from silence, not loss. Check packets_lost=0 in the detail: that is the proof.
sndbuf_err / rcvbuf_errKernel UDP counters in the header. Non-zero means datagrams were dropped locally. This is the number to pull off an AKS node.
negotiated protocolIn the blast summary. Blast itself is HTTP/3-only (ALPN h3), so HTTP/2 here means you pointed at the wrong client, not a silent fallback. Use curl h3 / Chrome h3 for a second stack.
omittedOpen-loop ticks dropped because max-inflight was full. That is coordinated omission: the generator could not start the request on time.
used_0rttSecond dial of the 0-RTT probe reused a session ticket. First dials are always 1-RTT.

The three timeouts interact

Who reports a failure depends on the ordering of the client timeout, the edge origin timeout, and the origin's own latency.

conditionresult
client > edgeClean 524. The classic case.
client < edgeClient sees client_deadline, the edge logs nothing. Very confusing in production.
no keep-aliveIdle connections die during long origin waits even with zero packet loss.

Testing a real tunnel

Set trust to system CA, runner to host, and always set an rps limit. Run Probe first: if it reports that UDP/443 is blocked on your network, a blast result would be meaningless. Get authorisation before pointing sustained load at someone else's production.

Closed-loop vs open-loop

Closed-loop (default) has N×M workers that wait for each response. When the origin slows down, completed RPS collapses. Open-loop starts requests from a token bucket at the configured rps regardless of in-flight latency, and counts omitted when max-inflight is saturated. Use open-loop when you want to hold offered load through a 524 window.

Impairment caveat

tc netem attached to root on a container veth is not applied evenly across TX queues, so request counts and medians vary a lot between runs. Trust the kernel counters and the latency tail.

SndbufErrors moves reliably with a rate cap. RcvbufErrors needs the receiving process to stall, which this lab has not reproduced on Docker Desktop. Use scripts/rcvbuf-pressure.sh on native Linux, or treat a zero rcvbuf counter as inconclusive rather than a pass.

Safety

This panel shell-executes docker and tc on your machine. It binds to 127.0.0.1 only, builds every command as an argument list rather than a shell string, and validates inputs against allow-lists. Do not expose it on 0.0.0.0.
